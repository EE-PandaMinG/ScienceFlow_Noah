# LNR storage telemetry

## Goal

Show each task's current storage cost as `Disk` in the TUI without making the interface
recursively scan active workspaces. Storage accounting belongs to LNR, which
already visits research files while producing recoverable stage snapshots.

## Accounting boundary

`Storage` means disk space generated by the ScienceFlow run:

- worker workspaces and snapshot object stores;
- task logs and state;
- submissions, merge outputs, reports, and report assets present when the
  managed run finishes.

It excludes read-only task inputs:

- every directory named `dataset`, at any level;
- the configured `input_data_dir` when it resides below the task root;
- every symlink target, whether local or external.

This boundary is deliberate. A 200 GB input dataset must never add a 200 GB
walk to run finalization and must not be reported as ScienceFlow-generated
storage.

## Implemented data flow

1. `WorkspaceSnapshotStore.capture()` already computes
   `logical_size_bytes` and `new_physical_bytes` while saving a stage.
2. LNR projects those existing counters to
   `task_logs/storage_latest.json` and appends an audit event to
   `task_logs/storage_events.jsonl`. This step performs no extra traversal.
3. Concurrent workers update the task projection under an advisory file lock;
   the latest document is replaced atomically.
4. After final report generation and before the managed process exits, the
   supervisor performs one generated-artifact scan. It skips datasets before
   entering them, does not follow symlinks, and deduplicates hard links by
   device/inode before summing allocated blocks.
5. The TUI reads only `storage_latest.json`. It never calls `du`, `os.walk`, or
   an equivalent recursive scanner.

Running values are partial estimates and render with `~`, for example
`Disk ~36.2M`. The terminal value is the calibrated physical allocation and
renders without the marker. If any path cannot be measured, the terminal sample
remains approximate.

## Log contract

`storage_latest.json` is schema version 1. Its stable presentation fields are:

- `total_bytes`: task storage value shown by clients;
- `exact`: whether the value is terminal and complete within the accounting
  boundary;
- `source`: `snapshot_counters` or `final_generated_storage_scan`;
- `sampled_at_utc`: sample time.

Additional fields retain per-worker snapshot counters, measurement details,
coverage, and exclusions for diagnostics. Clients should ignore unknown fields.
The accounting sidecars themselves are excluded so writing the terminal sample
does not immediately make its own value stale.

## Task-row presentation

The task overview keeps one physical terminal line per task. It reserves the
metrics and time-budget progress tail first, then assigns every remaining cell
to a task-name Top-K projection:

- task names use terminal cell width, including double-width CJK characters;
- K consumes all cells left after the fixed metric/progress regions and ends
  with an ellipsis when needed; it has no independent hard cap;
- the expanded card renders `row_full_name`, so the list projection does not
  discard the canonical name;
- narrow rows use `B / Es / Ec / D`, medium rows retain `Best / ESTRA / EEC`,
  and sufficiently wide rows render the full labels;
- the time-budget bar uses 10 cells on wide panels and 6 on narrow panels;
- the fixed-width cost value is rendered after the progress bar at the far
  right; its currency marker provides the label and the bar separates it from
  the research metrics;
- expanding a task keeps the progress bar on its summary row.

The visible rows form a table. The renderer measures the longest visible task
name and uses that as the shared name-column width, capped only by the space
required to keep the row on one line. B/Es/Ec/D therefore begin at the same
terminal columns on every row. Progress and cost remain right-aligned; any
unused width sits between the metric block and progress rather than changing
the metric-column positions.

The tier thresholds are based on the task panel's actual content width rather
than the outer terminal width. Tests cover 80, 100, 120, and 140-column
terminals and assert that the visible task-name width increases monotonically.
